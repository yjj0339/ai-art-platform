# 技术决策记录

## 使用规则

重要产品方向、数据结构、共享接口、外部服务、部署方式和会影响旧功能的决定，必须在这里记录。小型样式调整和普通缺陷修复不需要新增决策。

每条决策包含：背景、候选方案、最终选择、原因、影响、回退方式和状态。改变已生效决策时新增一条记录，不直接删除旧记录。

## 决策 001：学生报告优先采用 H5

- 状态：已确认
- 背景：完整自由拖拽 PPT 或 H5 编辑器复杂度高，维护和稳定上线成本过大。
- 选择：使用“4 套系统内置 H5 版式组件 + 后台配置模板”。
- 原因：更适合当前 MVP，学生使用路径更简单，生成和分享更稳定。
- 影响：学生只选择模板并生成；后台不开发完整自由拖拽编辑器；分享海报带二维码。
- 回退方式：保留现有报告数据结构；改变方向前评估模板迁移成本并获得用户确认。

## 决策 002：项目统一使用 pnpm

- 状态：已执行
- 背景：项目实际 `node_modules` 使用 pnpm 目录结构，而当前运行环境没有 npm 命令。
- 选择：保留 `pnpm-lock.yaml`，安装和构建命令使用 pnpm。
- 原因：锁文件、实际依赖布局和可用运行时保持一致，避免无法复现安装环境。
- 影响：服务器使用 `pnpm install --frozen-lockfile` 安装依赖；不再维护 npm 锁文件。
- 回退方式：如需切换包管理器，先在独立分支重新生成锁文件并完成全量构建与回归。

## 决策 003：业务数据与代码发布分离

- 状态：已确认
- 背景：`server/data` 保存课程 PDF、视频、模型和报告配置，发布覆盖会造成数据丢失。
- 选择：服务器通过 `AI_DATA_DIR` 使用独立持久化目录。
- 原因：代码可以重复发布，业务数据必须跨版本保留并独立备份。
- 影响：`server/data` 不提交到普通代码仓库；部署前迁移并备份数据。
- 回退方式：保留本地数据副本，从备份恢复到可写的数据目录。

## 决策 004：任务采用风险分级质量门禁

- 状态：已执行
- 背景：只写“完成后检查”过于笼统；所有任务一律全量测试又会造成无效工作。
- 选择：所有任务做差异检查，代码任务按前端、接口、AI、数据和部署类型执行对应最低检测，并对受影响旧功能回归。
- 原因：让“完成”有证据，同时保持测试成本与风险匹配。
- 影响：无法完成必要检测时只能报告未验证、部分完成或被阻塞。
- 回退方式：根据实际缺陷和迭代效率调整检测矩阵，但不得取消真实验证和回归要求。

## 决策 005：H5 报告采用服务端状态记录与模板快照

- 状态：已执行
- 背景：浏览器本地报告不能支持管理员审核、家长跨设备查看、公开分享和报告下架。
- 候选方案：继续使用浏览器本地数据；只把分享页导出为静态文件；建立服务端报告记录和随机分享令牌。
- 选择：服务端保存报告、模板快照、生成元数据、审核状态与不可猜测分享令牌；三端共用同一 H5 渲染器。
- 原因：可以形成学生提交、管理员审核、家长访问和下架失效的完整闭环，同时保证已有报告不因模板后续修改而改变。
- 影响：报告状态统一为 `draft`、`pending`、`rejected`、`published`、`offline`；只有已发布报告可以公开读取。
- 回退方式：保留报告页面数据和模板快照，可将服务端记录迁移到数据库或重新导出为静态成品，不依赖浏览器本地缓存恢复。

## 决策 006：AI 玩法复用现有无限画布并采用动态学生页面

- 状态：已执行
- 背景：原 AI 玩法中心只有表单和 JSON 配置，无法直观配置工作流，也无法为不同玩法设计不同的学生输入页面。
- 候选方案：重新开发独立工作流画布；复用现有无限画布；继续使用表单配置。
- 选择：现有 `CanvasStudio` 增加后台管理模式，玩法配置保存画布快照、学生页面栅格和运行参数；后台预览与学生端共用同一页面渲染组件。
- 原因：避免出现两套画布，保留节点、连线、缩放、撤销和保存能力；玩法发布后可通过数据库动态增加，无需每个玩法单独开发页面。
- 影响：玩法发布前必须完成真实接口测试；第一版只支持 Agnes 与火山引擎，不开放脚本、循环或任意 HTTP 节点；学生不能编辑工作流。
- 回退方式：已发布版本保存不可变配置快照，可恢复历史版本为草稿；代码回退时保留玩法版本表和备份数据库。

## 决策 007：无限画布采用节点级生成配置与确认式 AI 助手

- 状态：已执行，浏览器实机验收待补充
- 背景：原画布中的文生图、图生图和图生视频只是静态卡片，视频运行与 AI 助手使用固定演示结果；上传图片还会被固定比例裁剪。
- 候选方案：更换无限画布框架；继续在全局设置中堆叠参数；保留 VueFlow 并把生成状态、输入、输出和参数放到各自节点。
- 选择：继续复用现有 VueFlow；创作入口统一为上传、文字生成、图像生成、视频生成；自由文字不参与工作流；AI 助手先返回受限建议，用户确认后才应用。
- 原因：修改范围集中在现有画布，能够复用节点、连线、撤销和服务端文档；节点级数据更适合保存、恢复、连接和失败重试，也不会继续把模拟结果伪装成正式功能。
- 影响：画布文档版本升级为 2，但保留原节点基础类型并通过 `data.mode` 区分；旧文字、提示词、图像和视频节点在学生画布加载时自动迁移；新增画布助手接口 `/api/ai/canvas/assistant`。
- 回退方式：节点基础类型、旧字段和版本 1 数据仍可读取；回退前保留服务端画布文档，移除 `data.mode` 新界面后仍可按旧节点卡片展示。

## 决策 008：并行验证参考图驱动的AI整页图片H5

- 状态：测试分支已接通，尚未替换正式链路
- 背景：现有结构化H5与确认的产品设计效果图差距较大，用户希望后台上传完整竖版参考图，再使用学生真实素材和第一人称文字生成完整单页报告图。
- 候选方案：继续只扩展结构化HTML模板；直接用AI生成含全部中文的整页图；以参考图驱动视觉生成，并保留可校验的数据和正式发布边界。
- 选择：保留现有H5后台、学生端和正式报告链路，新增并行的整页视觉测试分支；后台参考图、草稿和发布配置使用服务端持久化，学生端只读取已发布配置。
- 原因：可以先验证视觉效果和真实模型稳定性，不在效果未确认前删除已经存在的报告能力，也避免把后台草稿直接暴露给学生。
- 影响：参考图只控制构图、色彩、背景、装饰和层级；学生作品、草图、AI图、3D图、环境图和自述才是实际报告内容；真实AI整页出图、准确中文拍平与家长正式页面仍需后续验证。
- 回退方式：关闭模板的 `visualGeneration.enabled` 或停止使用整页视觉测试入口，现有结构化H5继续工作；测试分支资源与配置可独立停用，不迁移或删除旧报告。

## 决策 012：图像供应商的「参考图能力」改为显式声明 + 公共层统一写入

- 状态：已执行（本地假平台全链路已验证；真实平台图生图未实测）
- 背景：无限画布允许把上游图片节点和「标记元素」接到图像生成节点，界面也会显示上游缩略图。但服务端各供应商的适配函数是各写各的：Agnes 写了参考图转发（`extra_body.image`），火山方舟 doubao-seedream 与 OpenAI gpt-image-1 从头到尾没有把 `image` 写进请求体，导致「界面显示有上游图，模型其实只收到文字」的静默失效。用户无法从界面察觉，只能靠对比出图发现。
- 候选方案：
  1. 只给火山和 OpenAI 各补一次 `image` 字段（最小改动，但下一个新平台会再犯一次）；
  2. 为每个供应商声明参考图协议，并在公共层统一解析、统一写入、加防静默守卫；
  3. 引入统一的图像生成 SDK 抽象层（改动过大，超出当前 MVP 需要）。
- 选择：方案 2。
- 原因：问题根源不是漏写两行，而是「参考图怎么传」这件事没有任何契约和检查点。方案 2 把能力变成可声明、可配置、可断言的事实，新增平台时不需要再各写一遍，也不可能再静默失败。
- 影响：
  - 每个供应商新增 `imageInput` 声明，取值 `body-field`（顶层 image 字段，火山方舟）/ `extra-body-image`（Agnes）/ `edits`（OpenAI 走 `/images/edits` multipart）/ `none`（明确不支持）。未声明时按 OpenAI 兼容处理并回传提示。
  - `generateImages()` 统一解析参考图并传入各适配器；`applyReferenceImagesToPayload()` 是全项目唯一的写入出口。
  - 声明 `none` 的供应商在用户传图时直接报错，不再静默丢弃；「收到图但转发数为 0」会触发守卫报错。
  - 管理后台新增「参考图能力」配置项与列表角标；「测试连接」可选真实出图自检（会产生一次出图费用）。
  - 新增验收脚本 `scripts/verify-provider-reference-images.mjs`（默认零费用，`--live` 才调用真实平台）。
- 回退方式：参考图声明与写入逻辑集中在 `providerImageInputSpec()` / `applyReferenceImagesToPayload()` / `generateImages()` 三处，回到旧行为只需在 `generateImages()` 不再统一解析、各适配器恢复自行处理；后台 `imageInput` 字段为可选，旧配置文件缺少该字段时按 OpenAI 兼容处理，不会报错。

## 决策 013：文本节点「编辑」卡片不再单独造一套，直接复用生成节点的卡片与提示词链路

- 状态：已执行（真实浏览器已验证；未调用真实付费文本模型）
- 背景：无限画布上图像/视频节点选中后弹出的是 `image-composer-panel`（上游小图标 + `@` 引用片 + 模型下拉 + 生成按钮），而文本节点点「编辑」弹出的是一张结构完全不同的卡片：一个裸 `textarea` + 写死的两个选项「创作 Agent / 提示词专家」。后果不只是「长得不一样」：那张卡片的输入既不能引用上游素材，模型下拉列出的也根本不是后台配置的文本模型（`'创作 Agent'` 会被服务端识别为「未指定模型」而回落到默认），而且发完只弹一句「内容已发送给智能体」，返回的文字从未写回节点 —— 点了等于没点。
- 候选方案：
  1. 保持独立卡片，单独给它补上游图标 / @ / 文本模型下拉（三处新代码，日后再加能力还要补一遍）；
  2. 直接把生成节点的卡片（`image-composer-panel` + `node-prompt-shell` + `inline-prompt-editor` + `inlinePromptParts` 引用片渲染）复用到文本节点，只把底部控件由「模型 + 比例 + 生成」收成「文本模型 + 发送」；
  3. 把文本节点并入生成配置节点（改动过大，且会改变既有画布结构）。
- 选择：方案 2。
- 原因：`@` 引用、引用片渲染、光标插入、marking 元素片、撤销/保存，全部已经挂在 `data.promptParts` 这一条链路上。只要文本节点也把卡片输入接到同一份 `promptParts`，这些能力**零新增代码**自动获得，且以后新增能力（例如新的引用类型）只需改一处。方案 1 会重演「图像/视频/文本三套各写各的」这种迟早会漏的老问题。
- 影响：
  - 文本节点卡片改为 `node-follow-panel image-composer-panel text-agent-panel`，输入框改用 `inlinePromptParts(data, id, false, true, false)` + `updateInlineGeneratorPrompt` + `commitInlinePrompt` + `setGenerationConfigNodePromptRef` + `handlePromptEditorClick`，`@` 走既有唯一入口 `insertReferenceToPrompt()`。
  - 卡片输入即节点自身的 `data.prompt` / `data.promptParts`（生成指令），不再是临时缓冲 `textAgentInput`；该 ref 已删除。
  - 模型下拉改为 `textAgentModels`（= 后台已配置的文本模型 `configuredTextModels`），并在发送时一并带上 `provider`（取自 `configuredModelProviders`），避免模型名落到别家平台。`generatorModels()` 对文本节点也改为返回文本模型，`'创作 Agent'` 只保留为 `generatorModelLabel` 的历史显示名。
  - 发送语义补全：消息 = 上游文本 + 提示词结构片（`effectiveGeneratorPrompt()`），已生成过文字时追加「原文：…」；返回结果写回 `data.output.text` **并同步 `data.text`** —— 因为节点正文 `smartTextValue()` 优先读 `data.text`，只写 `output.text` 会出现「生成成功但界面毫无变化」。
  - 卡片外观与图像节点逐项一致（宽度 390px / 背景 #fffefa / 圆角 14px / 内边距 14px / 描边 #d7d3cc），仅底部控件区多一条 `.text-agent-controls` 两列栅格覆盖。
  - 新增验收脚本 `scripts/verify-canvas-text-node-card.mjs`（零费用，stub 平台）；`scripts/verify-canvas-marking-mode.mjs` 中「挂 setGenerationConfigNodePromptRef 的模板数量」断言由 3 改为 4。
- 回退方式：文本节点卡片是唯一改动点。回到旧行为只需把该 `<div>` 恢复为 textarea 版本、恢复 `textAgentInput` ref 与 `'创作 Agent' / '提示词专家'` 选项；`generatorModels()` 的文本分支与 `defaultTextModel()` 可保留（它们只影响新建文本节点的默认模型名，不会破坏旧画布，旧画布里写的 `'创作 Agent'` 会被安全纠正为已配置文本模型）。

  - **关键技术约束（易踩）**：VueFlow 节点层用 `v-memo([node.id])` 缓存节点，父组件状态变化**不足以刷新节点插槽**；放大态需要节点内 DOM 变化，靠换 `nodes` 数组或换 `node.data` 引用都无效，必须用官方 `updateNodeData(id, data, { replace: true })` 并同步 `node.data`，才能触发重渲染（封装为 `refreshNodeSlot`）。

- 回退方式：删除三处 `<Teleport>` 包裹与 `.composer-head` 按钮行、移除 `promptZoomNodeId` 相关状态/函数与 Esc 分支，并把 `.node-follow-panel.image-composer-panel / .video-composer-panel` 的宽度改回 390px、输入框恢复原行高即可。

## 决策 018：文字节点走「只看上游、只写正文」的独立生成链路（2026-10-31）

- 状态：用户确认「按建议 1+3 一起做」并明确「DeepSeek4.1 这个模型是可以读图的」；代码已落地，服务端与前端两套验收脚本全绿，真实付费模型出文尚未实测。

  1. **图根本没进请求**：文字节点走的是画布助手的通用接口 `runCanvasAssistant()`，它的 `upstream` 上下文只带 `prompt` / `text` 两个字符串字段，上游图片节点的 `output.url` / `image` 从未被收集进 `messages`。所以模型从头到尾只看到文字（甚至只看得到节点的 `prompt`，看不到上游节点正文），自然「读不到图」。
  2. **返回的不是正文**：同一条链路复用的是工作流 Agent 的提示词，它会输出一份「我做了什么」的 JSON（actions / 说明），而前端把这段自述当正文写回节点；另有模型在没拿到图时会「合理推测」画面内容（`looksLikeCanvasBlindNote` 的场景），写回的文字看起来很像但是假的。
- 候选方案：
  1. 让上游图片进入文字生成请求（多模态 `image_url` data URL），并给文字节点一条专用提示词；
  2. 修模型配置，把文字节点的默认模型改成多模态模型；
  3. 拦住「AI 工作汇报 / 自述 / 瞎说」被当正文写回；
  4. 只在前端把上游图片拼成文字描述喂给模型（等于让模型看二手转述，画面细节必失真）。
- 选择：**1 + 3**（用户拍板）。方案 2 属于配置操作，已在配置层落实（见影响）；方案 4 明确排除 —— 文字描述转述会丢掉构图、颜色、材质这些用户真正要的信息。
- 原因：用户要的是「看图写文案」，那么图就必须以图片形式出现在请求里，这是无法靠提示词弥补的硬条件；而「返回自述」是一类**静默错误**（节点里出现了文字、看起来成功，但内容是假的），必须显式拦截并报错，不能容忍。
- 影响：
  - 新增 `operation: 'generate-text'` 分流：`runCanvasAssistant()` 与路由层开头都判断该 operation 后直接走 `runCanvasTextGeneration()`，**不再复用工作流 Agent 的 actions 提示词**。
  - 读图模型优先级常量 `CANVAS_VISION_MODEL_PRIORITY = ['deepseek-v4.1-flash', 'agnes-2.5-flash', 'doubao-seed-evolving', 'gpt-4.1-mini']`（用户指定 DeepSeek4.1 优先）；`canvasTextModelCandidates()` 按此优先级在「后台已配置的文本模型」里挑选，逐个试到成功为止，全部失败时把每次的失败原因一并回传，避免「只报最后一个错」掩盖真实原因。

## 决策 019：文字节点的结构片（引用 / 标记）以「底层事实」为准，不信输入框 DOM（2026-10-31）

- 状态：已执行（`verify-inline-chip-integrity.mjs` 修复后连跑 3 次全 PASS，`verify-canvas-p2` 38/38 无回归）
- 背景：`verify-inline-chip-integrity.mjs` 出现**偶发**失败（约 2 次失败 / 5 次运行）：第 5 步刚确认「引用片还在」，第 6 步点一下「标记」按钮，`promptParts` 里的 `{type:'reference', id:'upload-1'}` 就没了。加中间快照后定位到**丢失发生在点「标记」的那一刻**（`s6a` 已经是 `refs:0`），而不是打标记之后。
- 根因：输入框是 `contenteditable`，chip 是 `contenteditable=false` 的原子节点；数据同步有两条路 —— 改数据（数据优先）和**从 DOM 回读后整块覆盖 `promptParts`**。后者在 chip 已经不在 DOM 里的时候执行，就会把片永久抹掉。chip 离开 DOM 有几种日常路径：光标紧挨 chip 退格 / Ctrl+A 重新打字（整块删掉）、chip 被拖拽换位过（真实 DOM 被手工移动，vdom 不同步，下次 patch 顺手删掉）、点其它按钮让输入框失焦（立刻触发 blur 回读）。所以它表现得像「偶发」。
- 候选方案：
  1. 不再从 DOM 回读，一切以数据为准（改动过大：用户正常打字是浏览器直接改 DOM，不回读就丢失用户输入）；
  2. 回读照旧，但给「结构片」加护栏：回读结果里缺了、而底层事实仍证明它应该存在的片，一律补回；
  3. 只在 blur 时不回读（治不了退格与拖拽两条路径）。
- 选择：方案 2。
- 原因：回读本身是必需的（否则用户键入的内容进不了数据），问题只在于**它把"界面上暂时没有"当成了"用户想删"**。结构片该不该在，本来就有权威来源 —— 引用片来自连线、标记片来自 `data.elements`。用底层事实校正回读结果，既保留实时输入，又不会丢引用。
- 影响：
  - `withPreservedElementParts()` 更名为 `withPreservedStructureParts()`，护栏从「只保 element」扩到「同时保 reference」：`element` 片看 `data.elements` 是否还有该元素，`reference` 片看连线是否还连着（含间接上游，沿 `edges` 走）；判据都取**当前实时数据**，不信老的 `promptParts`。
  - 引用片白名单**不能用 `nodeReferenceChips()` 的返回值**：它只收录「当前有内容」的节点，上游节点内容暂时被清空（正在重新生成）时会把合法引用误判成失效而丢掉 —— 改为直接沿 `edges` 收集上游 id 集合。
  - 补回时保持已有片原位、缺失的按 `data.promptParts` 原顺序追加末尾，并递增 `promptEditorDomKeys[nodeId]` 强制该输入框按数据重渲染一次（否则会出现「数据里有、界面上看不见」）。
  - **护栏的双向化（2026-10-31 收尾）**：护栏不能只「补回」，也要「剪掉」——用户主动断开连线后，`promptParts` 里残留的 `{type:'reference'}` 是脏数据（不渲染、也不影响生成，但数据与认知不一致）。剪枝判据同样取底层事实（连线不在了才剪），**且剪枝路径绝不递增 `promptEditorDomKeys`**：被剪的片本来就渲染不出来（渲染与剪枝用同一套底层事实），换钥匙反而会在用户打字时整块重渲染输入框 → 光标被抢、输入中断。
  - **护栏返回值必须保持引用**：没有脏片时必须原样返回传入的数组本身，不能返回 `filter()` 的新数组。每次键入都走这个函数，换新引用 = 每次都让 `promptParts`「变了」→ 触发整块重渲染，实测会让 `verify-canvas-prompt-card-zoom` 的 Teleport 放大态整组失败（面板留在节点内、屏上尺寸 0）。
  - 四个调用点（`updateInlineGeneratorPrompt` / `updateInlineGenerationConfigNode` / `syncPromptFromEditor` / `insertReferenceToPrompt` 里的预回读）全部走同一个护栏。
  - 验收脚本第 6 步新增三处中途快照（进入标记模式后 / 点图打标记后 / 退出标记模式后），把「哪一步丢的」写进日志 —— 偶发问题必须可定位，否则下次只能靠猜。第 9 步新增「断线后引用片被真正移除」断言：脚本必须显式把光标放到输入框末尾再用 `insertText` 键入并走真实 blur（直接 `click` 可能落在 chip 上拿不到焦点、`keyboard.type` 对全角字符不产生 input，两种写法都会让断言白测）。
  - `repro-element-part-loss.mjs`：种子画布里 `image-1` 挪到 `x:460`（原 `x:60` 被左侧工具栏盖住「标记」按钮，15 条流程全部超时）；支持 `ONLY=F01,F05` 只跑指定流程；ERROR 时把错误首行与关键堆栈行直接打进日志。
- 回退方式：把 `shouldKeep()` 的 `reference` 分支去掉即回到「只保 element」的旧行为；剪枝分支去掉 `hasStale` 判断即可关闭；快照日志可直接删除，不影响断言。
