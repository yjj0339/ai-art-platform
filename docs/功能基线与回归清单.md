# 功能基线与回归清单

## 使用规则

本文件记录项目当前可观察功能和回归入口。状态必须来自实际验证，不能因为存在页面或代码就标记为“已验证”。

状态定义：

- `已验证`：最近完成真实页面、接口或业务流程验证，并记录证据。
- `待重新核验`：功能存在，但当前没有足够的新鲜证据证明完整可用。
- `故障待诊断`：已有明确失效反馈，需先复现和定位。
- `演示或占位`：尚未形成真实可用能力。
- `被阻塞`：受凭据、网络、外部服务或环境限制，无法完成验证。

- 补的什么：上一节「文件」菜单只在本机存储模式验证过，服务端登录模式（`VITE_AUTH_MODE=server`）下「用户起的名字到底有没有存进服务端」一直没验。本节用内存桩后端 + `AUTH_MODE=server` 把整条链路跑通。
- 链路（两段，脚本必须按这个时序断言）：
  1. 刚进画布、用户还没起名 → 自动建一份文档，title 是默认名「未命名无限画布」；
  2. 用户点顶栏名字起名 → 走 `PATCH` 把 title 改成他的名字（**不是**再 POST 一份）。
- 守住的三条底线：① 服务端确实建了文档（不是只躺浏览器里）；② title 是画布自己的名字，任何时候都不能是项目名「电商广告视频」（那正是修复前的 bug）；③ 改名走更新、同一 `resourceKey` 不会变成新建，刷新后顶栏与素材库都显示同一个名字。
- 回归结果：`verify-canvas-name-server.mjs` **13/13 PASS，连跑 3 次全绿**。
- 脚本本身修的两个问题（都不是产品 bug，但会让验收假失败）：
  - **固定等待改成轮询保存状态**。原来用 `delay(1500)` 等保存落地，而 vite 首次按需编译 + 首屏请求会占满同源连接，首次 POST 实测要 1.2s 后才发得出去，1.5s 窗口正好卡在「正在保存」→ A 段四条断言全读到一个还没有任何 POST 的空状态。改为轮询 `.save-state` 文本直到不再是「正在保存」（上限 20s）。

## 学生端智能体：账号隔离（2026-11-14，用户硬要求）

- 用户原话：「肯定是需要做账号隔离的、A账号的智能体的对话不能变成B的，不能互通」。
- 改造前的问题（不是「没隔离」，是「隔离得不够硬」）：所有账号挤在同一个 `agent-memory.json` 里，靠 `owners[账号ID]` 分组。功能上 A 看不到 B（已有 curl 验证），但一个文件被写坏、被手工改、被并发覆盖，就可能整锅串；而且上架后文件会涨到几百 MB，每说一句话都重写整个文件。
- 现在三层保险（不是靠「同一个文件里分个组」）：
  1. **物理隔离**：一账号一文件 `server/data/agent-memory/<ID>-<hash>.json`，A 的对话和 B 的对话不在同一个地方；
  2. **文件名不撞**：`净化后的账号ID` + `sha256(账号ID)` 前 12 位。两个 ID 净化后长得一样（`a/b:c` 与 `a_b_c` 都会变 `a_b_c`）哈希不同，绝不会落到同一文件；
  3. **读时再核对 `userId`**：文件里记的账号跟当前登录账号不一致就当成空记忆，并在服务端打一行 `[agent-memory] 账号 xxx 的记忆文件里记的是 yyy，已按空记忆处理，避免串号。`。原则是**宁可忘记，不可串号**。
- 接口层没有「查某个账号的记忆」入口：GET/POST/DELETE 都只认当前会话的账号，前端改代码也拿不到别人的。`AUTH_MODE=server` 下 `/api/*` 未登录直接 401。
- 老数据自动迁移：`migrateLegacyAgentMemory()` 把老单文件里的账号按人拆成独立文件，规则是「新文件已有内容就不覆盖」，拆完老文件清成空壳（不删，可人工确认后再删）。`clear` 路径也会先迁移，否则「清空」只清了壳、下次读取又把老数据搬回来。
- 实际验证：`node scripts/verify-agent-memory-isolation.mjs` **30/30 PASS**，零花费。
  - 模块级 25 项：A 写 2 条自己读到 2 → B 读到 **0** → B 写 3 条 A 仍是 2（互不污染）→ 磁盘确实两个文件且 `userId` 各自正确 → 长得像的 ID 落到不同文件 → 同一 ID 文件名稳定 → **文件被改成别人的 `userId` 时读出 0**、恢复后完好 → A 清空只清自己、B 的 3 条一条不少 → 空内容 400 → 老单文件 2 个账号拆开且数据不丢、老文件清空、不会重复搬回 → 运维列表只列账号不含正文。
  - 真实浏览器 5 项：两个独立上下文分别登录 `ceshi2` / `ceshi3`，乙刚进来看不到甲的话 → 各说一句 → 互相看不到 → 接口层各自只拿到自己的 → 甲清空后乙的记忆还在。
- 连带回归：`node scripts/verify-agent-memory.mjs` 11/11 仍全绿（接口契约未变，前端一行没改）。
- 收尾：删掉了已迁移为空的旧单文件 `server/data/agent-memory.json`；测试产生的账号记忆文件在脚本结尾自行清空，工作区不留垃圾。
- 限制：未验证两个标签页并发写同一账号（单进程内是同步读改写，理论安全，未做压测）；未验证真实服务器磁盘满/只读时的报错提示。
