## 3. 评审分歧 —— 最终裁定（以此为准）

| 分歧点 | 曾出现的说法 | **最终裁定** |
|---|---|---|
| 幂等唯一索引几条 | 1 条／2 条／3 条 | **1 条，`kind` 进键**（data-engineer rev.3 定版）：`uq_credit_ledger_idem (org, user_id, kind, biz_type, biz_id) WHERE biz_id<>''`，**同时盖 consume / refund / admin_adjust / redeem / void**（admin_adjust 的 `biz_id`=前端 `requestId`；redeem/void 的 `biz_id`=codeId）。原"码操作另建一条不含 user_id 的索引"**撤销**（`redeemCode` 状态机 `status='issued'` 已保证一码只入账一次，那条索引会变死索引）。`chargeCredits` 用 `INSERT … ON CONFLICT DO NOTHING RETURNING` 再回查补全响应 |
| 账本金额结构约束 | 无 | 新增 `CHECK (amount = from_free + from_wallet)`，把"跨天作废金额差自证"焊成**结构不可违**（"免费额度转钱包"这类错账插入即拒），对账退化为单表达式、不枚举 kind。零成本（表空） |
| 对账口径 / total_* | 删列／派生／保留 | `balance = total_recharged − total_consumed`；数据侧复核后**一期仅 1 处缺口**：`adminAdjust` 负向（`credit-store.js:352-358`，balance 减了 `total_*` 没减）。一期只补这一处；`total_*` 派生化留二期 |
| 跨天退款 | 回填原日／全额进钱包／作废 | **方案 A（免费部分跨天作废）**：`quota_date=今天`→回填当天免费池+退钱包；`≠今天`→免费作废。**不变量：refund 行 `amount = from_free + from_wallet`**（同日 `from_free>0`；跨天 `from_free=0`、`from_wallet<原扣费`，**金额差就是被作废部分，账本自证**）；跨天统一用 `credit_ledger.refund_state`（'none'/'refunded'/'free_expired'）+ `free_forfeited` 标记（见 P0-C），**不再靠"有没有 refund 行"判断**；幂等锚点改为原子 `UPDATE … SET refund_state=$2, free_forfeited=$3 WHERE id=$1 AND refund_state='none' RETURNING *`（空=已处理→200 幂等）。`refund` 行 `quota_date` = **consume.quota_date（不是今天）**、`ref_ledger_id`=consume.id、返回体带 `forfeitedFree`。**AC-06 文案同步改为**："失败退回可用积分：当日额度当日退，跨天只退钱包部分" |
| from_wallet 语义 | 各写入点语义不一 | **统一定义为"真正进出钱包的积分"**（免费池变动只记 `from_free`）。现有 4 处同类 INSERT 的 `from_wallet` 全是 0（`credit-store.js:202/261/403/594-597`），一律由 0 改 `amount`；对账 1 条不变式（§3 上一条 CHECK 已焊死），无其他前提 |
| 价目命名 | 文档 §5.2 点号风格 | **短横线 5 个**（沿用代码风格）：`image_basic`(5)/`image_hd`(10)/`report_h5`(10)/`video_clip`(30)/`canvas_workflow`(10)。文档 §5.2 点号风格作废；补 seed `image_hd`+`canvas_workflow`。**`PRICE` 常量在 `credit-store.js:620-636` 是唯一权威主键**，前端/文档/DB seed 三处必须逐字对齐，否则静默 400 |

## 4. 数据库迁移硬约束（决定"改完能不能生效"）

- 积分 6 张表是老库**新增表**，但 `migrate-db.mjs:25/32` 每天跑 `credit-schema.sql`，dev 库可能已建过表 → **`CREATE TABLE IF NOT EXISTS` 不会应用任何新列**。
- 因此**所有结构变更一律幂等**：`ALTER TABLE … ADD COLUMN IF NOT EXISTS` / `DO $$ … $$` 守卫 / `DROP CONSTRAINT IF EXISTS … ADD CONSTRAINT`。**不要直接改 CREATE TABLE 期待生效。**
- **不要** `CREATE INDEX CONCURRENTLY`（在事务内会报错；积分表初始数据量小，直接建）。迁移**末尾加 `information_schema` 断言**，确保索引/约束真的建上（`migrate-db.mjs` 输出较宽松，别被绿字骗了）。
- 一次性数据订正（补齐价目、回填 `total_*`）单独放一次性脚本，不进每日迁移。
- `credit-schema.sql` 与 `schema.sql` 有同日 `grant_date`/`usage_date` 问题（`ai-skill-store.js:776/938/1228` 同用 `CURRENT_DATE`），**两张日额度表必须一起修**，否则跨零点对账错位。
- **三条迁移轨道（rev.4）**：① 新库/CI→改 CREATE 定义（仅空库生效）；② 已有库→文件末尾幂等 ALTER 块（可反复重跑）；③ 一次性手工→`DROP INDEX`/`DROP COLUMN` 只进人工部署文档、**绝不进重跑文件**（`DROP CONSTRAINT`+紧跟 `ADD` 同块、或 DROP 纯校验 CHECK 可进轨道 2）。**前提：6 张表任何环境均无数据**（未提交、`chargeCredits` 零调用），若有行须先回填再加约束。`migrate-db.mjs` 无版本表、每次启动整段重跑 3 个 sql，这是轨道 2 必须幂等的根本原因。
